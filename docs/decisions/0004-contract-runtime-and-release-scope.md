# ADR-004: 以多 Agent 任务合同运行时作为当前产品定位，按发布阻断项收敛首发

## 状态

已接受。细化并部分取代 [ADR-003](0003-long-horizon-goal-protocol.md) 的产品叙事；
保留 LHGP 协议名、标识、兼容窗口及规范／运行时／插件分层决策。
**2026-09-05 修订**：用户定下产品名——中文**「限期合同中枢」**、英文
**Deadline Contract Hub**；原文的「多 Agent 任务合同运行时 / Multi-Agent Task
Contract Runtime」降为系统类别描述。协议名、包名、CLI、数据格式仍不变。

## 日期

2026-09-05

## 背景

用户指出：当前系统更接近一个不需要 LLM 参与调度、能够容纳多份合同的跨 Agent
任务合同调度系统。源码支持这一判断：合同、Goal 计划和 attempt 独立持久化，
daemon 通过确定性规则处理风险、预算、候选和租约。现有 Goal 推进消费外部提交的
阶段计划，不等于系统已能独立理解目标并持续重规划。

此前以“远期目标”包揽全部产品含义，容易让读者误以为内置常驻规划模型、只能持有
一份合同，或能够保证任意目标准时完成。用户希望统一口径并优先发布；跨主机、
跨网络明确不在本轮范围。

## 决定

1. 中文产品名：**限期合同中枢**。中文产品定义：**独立于会话和模型的多 Agent 任务合同运行时，支持远期目标的持续推进与证据化验收。**
2. 英文产品名：**Deadline Contract Hub**；multi-agent task contract runtime 保留为
   类别描述。协议名继续使用
   **Long-Horizon Goal Protocol（LHGP，远期目标协议）**，不新增缩写，不更改包名、
   CLI、MCP 工具名、数据目录或数据库格式。
3. “运行时”涵盖合同授权、持久化、调度、执行监督、恢复及验收，不能缩成单纯定时器。
   “跨 Agent”当前指同一主机上已接入且获授权的执行者可替换，不暗示跨网络执行。
4. 调度内核不依赖 LLM。人或程序都可建立合同；模型可作为客户端、可替换执行者、
   独立语义验收者或未来可选规划器。不存在必须常驻、负责维持整个系统的“总控模型”。
5. 明确三种不同层次：多个合同共存；Goal 根据已提交阶段推进合同；可选规划器提出
   新计划。前两项已有实现路径，第三项属于后续增强。前两项也不代表全局最优调度
   或任意共享工作区并发安全。
6. 后续若增加模型规划器，只允许提出可验证的计划／修订建议；不得绕过授权、预算、
   审批及验收直接写入权威状态。关闭规划器后，合同运行时必须仍可工作。
7. 先收敛已承诺能力的正确性，再发布 Developer Preview；不把可选规划器、复杂 UI、
   跨主机／跨网络或严格墙钟结果保证作为首发条件。既有 Alpha 判据不得静默下调。
8. 本轮执行顺序及发布门槛由 [RELEASE-PLAN.md](../RELEASE-PLAN.md) 管理；
   [LHGP-SPEC.md](../LHGP-SPEC.md) 仍是语义权威。复现的控制权和预算错误不能
   因既有质量门通过而豁免，具体证据见[发布检查](../evidence/release-readiness-2026-09-05.md)。

## 考虑过且拒绝的方案

### 继续只称“远期目标协议”，不解释运行时类别

- 优点：无需更新入口文档。
- 拒绝原因：无法准确说明已有多合同管理、确定性调度及普通程序接入能力；也容易混淆计划推进与自主规划。

### 改名为通用任务调度器，立即全仓 rename

- 优点：容易理解后台派工用途。
- 拒绝原因：遗漏合同授权、接力证据和验收闭环；破坏兼容性与新定位无关，不值得阻塞发布。

### 先做一个常驻 LLM 总控，再发布完整远期目标产品

- 优点：可尝试自动拆解、动态计划和语义选择。
- 拒绝原因：显著增加成本、不确定性及权限边界，且不是用户要求的首发必要条件。

## 后果

- README、规范首屏、产品一页纸使用一致口径；旧 ADR 和真实运行归档保留，靠引用说明取代关系。
- 首发聚焦单机合同运行时；维护计划明确分离已复现阻断项、待验证风险与发布后增强。
- 发布能力声明只覆盖对应提交、环境和场景，不用“一次三阶段演示”替代“三个真实目标”的 Alpha 验证。
- 暂不增加任何执行权限、默认预算、调度算法或发布到外部的自动化动作。
